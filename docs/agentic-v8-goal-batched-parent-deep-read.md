# Agentic RAG v8 按 Goal 批量父块 Deep Read 改进设计

## 1. 背景与基线

当前 `PARENT_CONTEXT` 策略在每个 Goal 内对每个父块分别调用一次模型，再把通过判断的完整父块登记为 Evidence。该策略在 5 个案例中取得了最高的 Recall@5 和 AEC，但调用次数、token、耗时和失败面都会随父块数量线性增长。

ARH-036 在“每个文档最多读取 6 个父块”后的基线为：

| 指标 | 当前基线 |
| --- | ---: |
| Recall@5 | 1.0000 |
| 父块候选池覆盖 | 0.9362 |
| AEC | 0.5745 |
| RCC | 0.6596 |
| 接受父块 | 3 / 7 |
| 完整链路耗时 | 51.9 s |
| 总模型 token | 26,775 |
| 父块 Deep Read 逻辑调用 | 7 |

关键错误是：包含标准答案原文的父块已经被召回并传给 Deep Read，但被二元父块判断错误拒绝。

## 2. 目标与非目标

### 2.1 目标

1. 一次问题分析模型调用完成独立问题改写、1 至 3 个 Goal、Requirement 和每个 Goal 的首轮双路 Query。
2. 每个 Goal 的所有已选父块只使用一次批量 Deep Read；不同 Goal 的 Deep Read 并发执行。
3. 每个 Goal 独立进行一次 Evidence Judge；不同 Goal 的 Judge 并发执行，并可分别生成一次补检 Query Pair。
4. 需要补检的 Goal 并发执行检索、重排和一次批量 Deep Read。
5. 最终仍把通过判定的完整父块作为 Evidence 组装给回答模型，保持策略二的上下文完整性。
6. Deep Read 必须看到触发父块召回的子块锚点，但只承担父块级证据判定；不再把精确摘录作为接纳父块的前置条件。
7. 同时优化 Recall、AEC、耗时、token、逻辑调用数和模型失败面，而不是只优化单一覆盖指标。

### 2.2 非目标

1. 本轮不修改向量模型、关键词检索器和 rerank 模型。
2. 本轮不重新设计文档入库和父块切分，只在诊断中记录目录噪声问题。
3. 不使用固定长度 span 作为最终 Evidence。
4. 不把无法装入批量输入的父块静默丢弃；任何预算裁剪都必须持久化为可观测降级。
5. 第一阶段只以 ARH-036 为闭环案例，不据此直接替换生产默认策略。

## 3. 新策略：GOAL_BATCHED_PARENT

### 3.1 调用拓扑

```text
问题分析：1 次模型调用
  -> Goal 1/2/3 并发
       -> 每个 Goal 的 KEYWORD + SEMANTIC 并发检索
       -> 每个 Goal 独立 rerank
       -> 子块扩展、父块去重
       -> 每个 Goal 一次批量父块 Deep Read
  -> Goal 1/2/3 的 Evidence Judge 并发
       -> 各自判断 Requirement 覆盖并生成最多一次补检 Query Pair
  -> 需要补检的 Goal 并发
       -> 双路补检并发
       -> rerank、父块扩展与去重
       -> 每个 Goal 一次批量父块 Deep Read
  -> 汇总全部 Evidence
  -> 最终答案：1 次模型调用
```

设 Goal 数为 `G`、每个阶段每个 Goal 的父块数为 `P`：

- 旧策略父块 Deep Read 调用数约为 `G * P`，补检时再增加 `G * P`。
- 新策略父块 Deep Read 调用数为首轮最多 `G`，补检最多再增加 `G`。
- Evidence Judge 从一次全局调用调整为最多 `G` 次，但可以并发，输入更小且故障隔离到单个 Goal。
- 三个 Goal 完整执行首轮和补检时，新链路生成式逻辑调用的理论上限为：问题分析 1 + 首轮 Deep Read 3 + Judge 3 + 补检 Deep Read 3 + 最终回答 1 = 11。

### 3.2 Deep Read 输入

每个 Goal 的一次调用包含：

- 独立问题与当前 Goal。
- 当前 Goal 的 1 至 3 个 Requirement。
- 当前阶段的两条 Query。
- 所有已选、已去重的父块。
- 每个父块的 `parentChunkId`、`titlePath`、完整 `parentText`、检索分数。
- 每个父块内命中的子块文本、父块内起止位置、子块 ID、查询来源和分数。

子块只是阅读锚点，不是最终 Evidence。Deep Read 必须先检查锚点，再检查整个父块，允许在锚点之外发现直接证据。

### 3.3 Deep Read 输出

模型只返回应接受的父块；未返回的输入父块视为拒绝：

```json
{
  "acceptedParents": [
    {
      "parentChunkId": "UUID",
      "requirementIds": ["UUID"]
    }
  ]
}
```

接受规则：

1. 出现在 `acceptedParents` 中表示父块至少有一部分原文直接支持目标 Requirement；不要求单个父块完整回答整个 Requirement。
2. 接受项必须引用输入中的父块 ID 和合法 Requirement ID；只有一个目标 Requirement 时，允许省略 Requirement ID 并由后端补齐。
3. 未列出的父块视为拒绝。未知、重复或局部非法的接受项被逐项忽略，不再让一个坏条目击穿整个 Goal；只有顶层 JSON 契约无效时才进行一次 JSON Repair。
4. 兼容读取早期 `parentDecisions` 结构，但新 Prompt 只要求输出 `acceptedParents`，避免 14 个拒绝行消耗输出 token 并造成截断。
5. 通过判定后，完整父块进入 Evidence。Judge 使用后端从命中子块锚点取得的逐字阅读摘要，最终回答仍使用完整父块。
6. Deep Read 不再同时承担“相关性判定 + 精确引文抽取”。精确摘录不是父块接纳门槛，避免模型已识别事实却因复制引文或 JSON 细节失败而丢掉证据。

### 3.4 三个提前截断点的修正

ARH-036 的最新逐阶段诊断发现，正确父块的命中子块位于 rerank 第 12 名，但在它之前同一文档已有 6 个不同父块，因此被“每文档最多 6 个父块”规则截断；即使 Deep Read 接受更多父块，单 Requirement 最多 3 条 Evidence 的配额又会造成第二次截断。

本轮按如下顺序修正：

1. 父块仍按 rerank 顺序去重，但不再额外设置每文档 6 个的硬上限；只受每 Goal/阶段 14 个父块总上限约束。
2. 扩展证据档位把单 Requirement Evidence 上限从 3 提高到 6、每 Goal 上限提高到 18；ARH-036 单 Requirement 最多进入 6 个完整父块。
3. 批量父块输出改为布尔接纳，输出 token 显著缩短；模型不再复制引文。
4. 若结构化输出在一次 JSON Repair 后仍失败，首轮先记录为隐藏风险，不静默假装成功；实验确认主要误差后再决定是否增加可解释的召回兜底，避免一开始就把所有父块无条件放行。

### 3.5 Requirement 设计原则

Requirement 要描述“需要被原文核验的证据面”，不能预先猜测答案，也不能窄化为某个检索词。

- `DESCRIPTIVE`：核心 Requirement 覆盖定义、组成、职责、关系、主要内容或作用；不能因为找到一个操作命令就认为概述已经完整。
- `OPERATIONAL`：核心 Requirement 覆盖主要做法或过程；只有用户问题确实要求时，才增加前置条件和限制。
- 比较问题按比较维度拆分，而不是按关键词拆分。
- 列举问题要求覆盖原文明确列出的主要项目，不能找到一个项目就判定完整。
- 每个 Goal 保持 1 至 3 个 Requirement，避免过细拆分导致调用输入和 Judge 输出膨胀。

Deep Read 的判断对象是稳定 Goal 和 Requirement；Query 与 matchedChildren 只用于定位，不能把“没有命中 Query 字面词”作为拒绝理由。

### 3.6 每 Goal Evidence Judge

Judge 只接收一个 Goal，并读取：

- Goal 和 Requirement。
- 已接受父块的 Evidence ID、titlePath、Requirement 关联。
- 后端从命中子块锚点截取的逐字阅读摘要；不重复发送所有完整父块，减少 Judge token。该摘要只帮助 Judge 定位，父块是否进入 Evidence 仍由 Deep Read 的布尔判定决定。

Judge 对每个 Requirement 输出 `COVERED` 或 `MISSING`。`COVERED` 必须引用直接支撑该 Requirement 的 Evidence；证据数量不能代替覆盖完整性。缺失时生成一对互补的 KEYWORD / SEMANTIC 补检 Query。

不同 Goal 的 Judge 由虚拟线程并发执行，并受 Goal 级最大并发 3 的信号量约束。某个 Goal 的 Judge 失败时只对该 Goal使用确定性补检降级，不影响其他 Goal。

### 3.7 token 与时间控制

1. 每个 Goal 只重复一次系统提示、Goal、Requirement 和 Query，消除逐父块调用的重复 token。
2. ARH-036 的 7 个父块必须完整进入同一次调用，不允许裁剪。
3. 批量输入采用明确的 token 预算检查。超过预算时先减少低排名且与已选父块重复的候选，但必须记录 `BATCH_INPUT_TRIMMED`、被裁父块 ID 和估算 token；不得静默截断父块文本。
4. 首轮与补检分别最多一次 Deep Read，不因为单个父块被拒绝而普遍增加第二次模型调用。
5. 查询对、Goal、Judge 和补检均在已有虚拟线程执行器上并发；并发上限为 3，避免同时压垮上游模型 API。
6. 记录每个阶段的逻辑调用、物理尝试、输入/输出 token、模型累计耗时和墙钟耗时。
7. 结构化模型调用遇到 429 或 5xx 时，允许在同一逻辑调用内进行一次带随机退避的原请求重试；该物理失败和重试必须分别持久化。只有模型成功返回但 JSON 契约无效时，第二次尝试才用于 JSON Repair，两类重试共用两次物理尝试上限。
8. 评测以最终失败的逻辑调用判定链路是否降级；一次已经恢复的 5xx 仍计入 `modelFailedAttemptCount`，但不会把最终成功的逻辑调用误判为整条链路失败。

## 4. ARH-036 验收标准

### 4.1 硬门槛

- 完整链路严格成功，不接受受控降级作为正常结果。
- Recall@5 保持 `1.0000`。
- 包含客户端/服务端核心原文的父块不能再被拒绝。
- AEC 高于当前 `0.5745`。
- 首轮父块 Deep Read 从 7 次降为 1 次。
- Judge 阅读摘要全部来自父块中的命中子块，并通过后端逐字校验。

### 4.2 目标值

- AEC 达到 `0.90`，或与父块候选池覆盖上限 `0.9362` 的差距不超过 `0.05`。
- 根据后续确认的产品取舍，覆盖优先于 ARH-036 旧版 `26,775` token；五案例平均目标约为 `50,000` token，复杂多 Goal 案例允许小幅超过。
- 完整链路耗时尽量不高于旧五案例均值 `63.5 s`；考虑外部 API 抖动，同时报告模型累计耗时和墙钟耗时，不以单次网络抖动作唯一结论。
- RCC、citation entailment 和最终答案语义分不低于基线。

### 4.3 迭代规则

1. 先运行一次当前基线复核环境可比性，再运行新策略。
2. 若 Recall 或 AEC 未过硬门槛，检查父块是否进入批量输入、Deep Read 判定和证据池配额，针对最早发生损失的阶段修改。
3. 若覆盖达标但 token 未下降，减少重复输入、父块判定输出和 Judge 阅读摘要长度，不先缩小父块候选池。
4. 若覆盖和 token 达标但耗时不降，检查并发槽、模型调用排队和 JSON Repair；不通过牺牲 Recall 来掩盖 API 排队。
5. 每轮只改变一个主要变量，并在报告中保留运行 ID、配置、代码版本和逐父块判定，直到通过硬门槛；目标值若受外部 API 抖动影响，至少重复验证一次。

## 5. 实施顺序

1. 新增 `GOAL_BATCHED_PARENT` 实验策略，保留现有三种策略作为对照。
2. 实现按 Goal 批量父块输入、matchedChildren 构造和布尔输出解析。
3. 扩展父块 Evidence，使 Judge 可使用后端验证的命中子块摘要，而最终回答仍使用完整父块。
4. 实现 v8 新策略下的每 Goal 并发 Evidence Judge，并调整预算上限和调用键。
5. 增加单元测试：批量父块完整判定、非法 Requirement、遗漏父块、子块锚点、调用预算和多 Goal Judge 合并。
6. 编译并运行模块测试。
7. 在隔离数据库和隔离 API 实例中只运行 ARH-036，记录并迭代。
8. 通过单案例门槛后再决定是否扩展到 5 个案例和是否设为默认策略。

## 6. 风险与控制

- **批量输入过长**：显式预算与可观测裁剪；禁止截断单个父块。
- **模型漏判某个父块**：matchedChildren 锚点、逐父块完整输出契约、取消每文档过早截断；若实验仍有假阴性，再增加可解释的锚点召回兜底。
- **模型过度接受**：Prompt 要求父块存在直接事实，Judge 再检查覆盖而非数量；最终回答仍受上下文 token 上限控制。
- **并发触发上游限流**：最大并发 3，失败隔离到 Goal，并记录排队与模型耗时。
- **Judge 调用从 1 增至最多 3**：每次输入只含单 Goal 和短命中子块摘要；用并发换墙钟时间，用更小上下文提高判断稳定性。
- **单案例过拟合**：ARH-036 只用于第一阶段闭环，设计保留现有策略开关，后续必须扩展样本验证。

## 7. 实施迭代与实验结果

### 7.1 关键迭代

1. 第一版要求模型为每个输入父块输出一行判定。五案例试跑中，两个大批次因输出截断而形成不完整 JSON；因此改为只输出接受项，并把 Deep Read 输出上限收敛到 900 token。
2. 旧评测器固定要求一次全局 Judge，错误地把“每 Goal 一次 Judge”的成功链路判成降级。评测器现同时接受旧拓扑（全局一次）和新拓扑（Judge 数等于首轮 Goal 数），且继续严格拒绝模型逻辑失败、隐藏证据和支持动作失败。
3. ARH-036 正确父块在旧策略中已召回但被逐父块 Deep Read 假阴性拒绝。新策略改为一次阅读 Goal 的全部父块、宽松接纳部分直接证据，并取消每文档 6 个父块的提前截断。
4. 首次最终五题试跑中 ARH-046 的 Recall 为 0。逐层检查证明 API 和链路均成功，但问题分析生成的泛化关键词没有召回标准文档。旧成功运行使用“应用场景”，标准文档位于关键词结果第 1。
5. 最终查询策略保留模型关键词，并在 Goal 含有可验证的简短主题时追加一个 `OR Goal主题` 分支。它不增加模型调用，也不覆盖模型原词；Prompt 同时要求保留用户明确给出的章节名或目标短语，避免只输出上位领域分类。

### 7.5 并发证据

### 7.8 v8 正式版本

200 题验收通过后，`GOAL_BATCHED_PARENT` 被提升为 v8 的正式默认策略。应用配置、Compose 配置和示例环境配置均使用该值；旧策略仍保留为显式回滚和历史复现选项。未配置 `RAG_AGENTIC_DEEP_READ_STRATEGY` 时，Deep 会直接执行按 Goal 批量父块链路。

正式档位命名为 `V8_FINAL_GOAL_BATCHED_PARENT`。它锁定 200 题检索与证据验收使用的参数集：每个 Goal 的关键词/语义 TopK 均为 60，RRF 与 rerank 输入上限均为 80，rerank 输出和每阶段父块上限均为 14；最多 3 个 Goal，搜索、rerank、Deep Read 并发分别为 6/3/3。结构化模型单次输出总闸门为 2,200 token，单次批量 Deep Read 输入预算 20,000 token、输出再单独限制为 900 token，总运行输入/输出预算 150,000/20,000 token，Deadline 为 240 秒。证据池上限为总计 36、每 Goal 18、每 Requirement 6、同父块同阶段 3。该 200 题验收使用 `AGENTIC_RETRIEVAL_ONLY`，没有执行最终答案生成，因此旧在线组装器的固定 8 条限制并未被这次验收验证。最终回答现按唯一父块和 token 预算动态组装，详见 `agentic-v8-final-answer-generation-v2.md`。上述数值会随每次运行写入 `runtime_snapshot`，避免只切换策略名却遗漏其他限制。
