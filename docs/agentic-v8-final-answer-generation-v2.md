# Agentic RAG v8 Deep 最终回答生成 v2 设计

## 1. 背景与问题

v8 `GOAL_BATCHED_PARENT` 已通过 200 题检索与证据验收：Recall@5 `0.9758`、AEC
`0.9191`、RCC `0.9373`。该验收使用 `AGENTIC_RETRIEVAL_ONLY`，只验证到
Accepted Evidence，没有执行最终答案生成。

当前在线 Deep 回答复用了旧的最终组装逻辑，存在四个问题：

1. 同一个父块支持多个 Goal 时会形成多条 Accepted Evidence，并重复占用最终引用槽位。
2. 固定最多 8 条记录，限制发生在父块去重之前，可能让 8 个槽位只代表 6 个唯一父块。
3. 最终输入预算只有 10,000 token，且估算未完整计入系统指令、会话历史和 JSON 开销。
4. 最终模型只看到证据列表，不知道每个证据支持哪些 Goal，容易生成扁平、覆盖不全的回答。

这些问题不影响 v8 的 Deep Read 与 Accepted Evidence 指标，但会浪费已经找到的证据，使最终回答
弱于检索能力，甚至弱于 Fast。

## 2. 目标与边界

### 2.1 目标

- 保留已经验证的 v8 检索、父块扩展、批量 Deep Read、Evidence Judge 和一次补检。
- 最终上下文以唯一父块为单位，同一父块只发送一次。
- 优先覆盖所有有证据的 Goal 和 Requirement，再按相关性利用剩余 token。
- 不再以固定 8 条作为主要截断条件；以输入 token 预算作为主要边界。
- 多 Goal 问题生成有层次的回答，单 Goal 问题保持直接，不制造无意义标题。
- 最终阶段仍只调用一次模型，不新增摘要、规划或二次润色调用。
- 保留逐事实引用，引用正文仍是完整父块。

### 2.2 非目标

- 不修改 v8 的召回、重排、Deep Read 和 Judge 策略。
- 不把所有 Accepted Evidence 强制引用；模型只引用实际支撑回答事实的父块。
- 不以“回答越长越好”为目标。目标是覆盖完整、结构清楚和信息密度高。
- 不把会话历史视为企业事实证据。

## 3. 最终证据装包

### 3.1 唯一父块合并

按 `(documentVersionId, parentChunkId)` 合并 Accepted Evidence。合并结果保留：

- 完整父块正文和 SourceAnchor；
- 所有支持的 Goal；
- 每个 Goal 下所有活跃 Requirement；
- 最高 retrieval score；
- 首轮/补检来源和检索来源。

同一父块支持多个 Goal 时，在最终请求中只分配一个证据编号，并把该编号同时列入对应 Goal 的
证据映射。

### 3.2 覆盖优先选择

候选父块按以下两阶段选择：

1. **覆盖阶段**：优先选择能新增 Goal 或 Requirement 覆盖的父块；新增覆盖更多者优先，之后按
   retrieval score 和较小 token 成本稳定排序。
2. **补充阶段**：在 token 预算允许时，按 retrieval score 继续加入尚未选择的唯一父块。

如果全部唯一父块都能放入预算，则全部进入最终上下文。只有超过 token 预算时才丢弃低优先级父块。
引用数量只保留证据池容量 36 的安全闸门，不再作为正常装包的质量上限。

### 3.3 Token 预算

v8 Deep 最终回答参数调整为：

| 参数 | 旧值 | v2 |
| --- | ---: | ---: |
| 最终输入预算 | 10,000 | 20,000 |
| 最终输出预算 | 2,500 | 4,000 |
| 最终引用正常上限 | 8 | 动态，最多 36 个唯一父块 |
| 最终模型调用 | 1 | 1 |

装包估算必须计入问题、系统指令、Goal 映射、会话历史、父块正文、标题、引用元数据与固定序列化余量。
最终请求构建后再次估算；超出预算时从补充阶段末尾开始移除，但不得优先移除某个 Goal 的唯一证据。

## 4. 回答提示与结构

最终模型请求增加紧凑的 Goal-证据映射，例如：

```text
目标 1：解释普通用户、服务账号和匿名请求的身份来源
可用证据：[E1] [E3] [E5]

目标 2：比较三者的凭据管理方式
可用证据：[E1] [E4] [E6]
```

系统指令增加三条规则：

1. 多 Goal 时按 Goal 顺序组织小节；单 Goal 不强制分节。
2. 每个有证据的 Goal 都必须得到回答，并至少引用一条映射到该 Goal 的证据。
3. 综合互补证据，保留条件、差异、步骤和例外；不要逐条复述证据，也不要为了少引用而遗漏事实。

这仍是一次最终生成调用，不增加串行延迟和额外模型失败面。

## 5. 引用与展示语义

- Deep 引用的 `quote_text` 必须与完整父块正文一致。
- `chunk_id` 必须指向 `PARENT`。
- 引用位置使用父块所有 SourceAnchor segment 的最小起点和最大终点，不能再只显示第一个 segment。
- 面板显示的是答案实际引用的唯一父块；Accepted、Packed、Cited 数量分别用于运行诊断，不能混称。

## 6. 验证方案

### 6.1 自动化测试

- 跨 Goal 的相同父块合并为一个证据。
- 合并后保留完整 Goal/Requirement 映射。
- 预算充足时不丢弃任何唯一父块。
- 预算不足时优先保持 Goal/Requirement 覆盖。
- 最终请求中不存在重复 `parentChunkId`。
- 多 Goal 请求包含 Goal-证据映射和分层回答指令。
- Deep 引用位置覆盖完整 SourceAnchor 范围。
- 非 Goal 批量策略保持原有行为。

### 6.2 代表性完整链路

先运行 ARH-001、ARH-021、ARH-036、ARH-046、ARH-051，再选择一个当前在线多 Goal 问题复验。
记录：

- Accepted 记录数、唯一父块数、Packed 唯一父块数和 Cited 唯一父块数；
- 最终上下文 expected-answer coverage；
- Goal 覆盖率、Recall@5、AEC、RCC；
- 最终答案语义分、引用支持分和引用可解析率；
- 最终输入/输出 token、完整链路耗时和最终生成耗时；
- 与当前 Deep 基线和 Fast 的回答结构、信息覆盖及引用数量对比。

硬性门槛：

- 最终上下文无重复父块；
- 预算能容纳时，Packed 唯一父块数等于 Accepted 唯一父块数；
- 每个有 Accepted Evidence 的 Goal 均有 Packed Evidence；
- 最终回答成功且所有引用可解析；
- Deep 的最终证据覆盖与回答覆盖不得低于改动前 Deep；
- 不新增最终模型调用次数。

## 7. 发布

测试通过后只重建当前隔离工作树的 API 与 Web/必要服务，不触碰其他 Compose 项目或工作区。
发布后验证：

- 当前容器运行 `agentic-rag-v8`、`GOAL_BATCHED_PARENT` 和 v2 最终回答参数；
- 本地与公网演示入口指向同一当前工作树 Web/API；
- 新建 Deep 多 Goal 会话，核对运行快照、唯一父块装包、回答结构、引用数量和完整父块正文；
- Fast 行为无回归。

## 8. 验收结果

2026-08-07 已在隔离数据库与隔离 API 上完成五案例 Deep 完整链路及 Fast 对照。Deep 最终达到
`5/5` 成功、Recall@5 `1.0000`、AEC `0.9519`、语义正确性 `0.9740`、引用支持
`0.9460`、引用可解析率 `1.0000`。五题均未丢弃预算可容纳的 Accepted 唯一父块。完整数据、
逐题 token、延迟与模型 API 重试记录见
`benchmarks/agentic-v8-final-answer-v2-five-case-20260807.md`。
