## 1. 文档目的

本文档用于统一 VerityForge 前端改版的产品目标、交互原则、页面结构和数据规则，作为后续设计稿、技术方案、任务拆分和验收的共同依据。

本文档不是聊天记录的逐字转录，而是将此前问答整理为可执行的需求决策。除明确列为“待核验”或“暂缓”的内容外，其余内容均视为当前需求基线。后续若有新结论，应直接修订本文档并记录变更，避免设计和实现继续依赖零散上下文。

本轮不包含：

- 前端代码实现；
- 视觉稿或高保真原型制作；
- 实施步骤、工期和优先级计划；
- 后端接口改造；
- Playwright 或浏览器联调；
- 公网映射调整。

## 2. 产品背景与问题定义

### 2.1 当前体验的核心问题

当前前端的问题不是单个组件不够精致，而是信息架构、视觉层级和交互行为同时失衡：

1. 侧边栏同时承载对话、知识库、记忆、评测、团队、安全、运行配置和账户信息，工作区边界不清晰。
2. 历史记录展开后会挤压账户区域，导致 `Administrator` 跳动，破坏稳定预期。
3. 首页使用过多图标、说明文字、模式按钮、任务卡片和装饰元素，首要动作“提问”反而不突出。
4. 对话输入区采用老式纸飞机图标、并列大按钮和大量辅助文字，显得僵硬且占用空间。
5. 对话消息采用重复头像、标签、边框和卡片，阅读体验不像连续文章，证据与正文也缺少层级。
6. 评测页将数据集列表、配置、计划、趋势、样例和运行历史堆在一个页面中，内容密度高但重点不明确。
7. 知识库详情把 Metadata 配置、索引配置、文档列表和文档检查器混在同一层级，用户难以判断当前任务。
8. 文档详情采用狭小弹窗或抽屉承载大量内容，无法舒适查看正文、分块、处理过程和版本。
9. 视觉上存在卡片过多、边框过多、圆角过多、装饰大于信息、配色单一等问题，整体缺乏现代感和可信度。

### 2.2 改版目标

VerityForge 的目标不是复制某一家大模型产品，而是达到现代企业级 AI 产品应有的基本质量：

- 简约、克制、清晰，首屏只突出当前最重要的任务；
- 对话空间适合日常员工和研发人员快速提问、阅读答案和核验证据；
- 管理工作台适合管理员完成知识库建设、评测和系统管理；
- 复杂信息按层级逐步展开，而不是同时展示；
- 页面结构和交互位置稳定，不因展开内容而产生无意义跳动；
- 状态、失败原因和处理进度透明，避免只呈现“看起来成功”的假象；
- 能删除的冗余信息不保留，不能帮助用户完成任务的组件不上屏。

### 2.3 目标用户与当前权限范围

产品体验面向两类使用场景：

- 对话空间：内部普通员工和研发人员的日常知识问答；
- 管理工作台：管理员进行知识、评测和系统治理。

当前版本只实现并展示 `ADMIN` 一个角色。暂不设计 Editor、Viewer 等角色的界面，也不在页面中暴露角色、成员权限或权限矩阵。组织和部门当前只作为文档 Metadata，不作为本轮前端访问控制条件。

## 3. 全局产品架构

### 3.1 采用双工作区架构

系统拆分为两个边界清晰的工作区，使用同一品牌和设计语言，但拥有不同的信息密度与导航结构。

#### A. 对话空间

用途：日常知识问答。

核心内容：

- 新建对话；
- 历史对话；
- 问题输入；
- 知识范围和 Metadata 筛选；
- `自动 / 快速 / 深度` 模式；
- 答案、引用和来源核验。

对话空间不承载知识库管理、评测、团队、安全和运行配置等管理导航。

#### B. 管理工作台

用途：知识建设、质量评测和系统治理。

核心模块：

- 知识库；
- 记忆；
- 评测；
- 团队；
- 凭据安全；
- 运行配置。

两个工作区通过账户菜单切换。管理工作台可以比对话空间更紧凑，但仍须保持明确层级和渐进式展开。

### 3.2 页面与操作层级

所有模块遵循以下层级：

1. 列表页用于寻找目标和发起主要动作；
2. 详情页用于理解一个对象的完整状态；
3. 二级页或标签页用于查看不同维度；
4. 抽屉或弹窗只用于短流程、确认和轻量编辑；
5. 大量正文、样例、日志、分块或版本信息必须使用完整页面，不塞入狭窄抽屉。

## 4. 品牌与视觉方向

### 4.1 品牌名称

产品名称统一改为 `VerityForge`。

不再使用 `RAG Workbench`、旧项目名称、旧图标和 `Knowledge operations` 等副标题。

### 4.2 品牌呈现

采用纯文字标识，当前不需要独立图标。建议：

- `Verity` 保持克制和清晰；
- `Forge` 可通过略强字重或细微色彩差异形成识别度；
- 不使用夸张艺术字、花体、立体效果或复杂渐变；
- 品牌只在必要位置出现，避免侧边栏和主内容区重复展示。

### 4.3 视觉基调

整体采用安静、现代、可信的企业级视觉：

- 大面积浅色中性背景；
- 深石墨色正文；
- 蓝色仅作为主要交互和选中状态；
- 绿色仅用于成功、证据或健康状态；
- 红色仅用于失败、风险和破坏性操作；
- 降低阴影、描边、圆角、渐变和装饰插画的使用频率；
- 避免整体被紫色、深蓝灰、米色或单一色系支配；
- 不做营销式首页、巨大 Hero、装饰性光球或无意义背景图形。

### 4.4 组件约束

- 每个页面只保留一个明确的主要操作；
- 卡片只用于重复对象、真实工具面板和必要弹层，不将每个区块都包装成卡片；
- 不在卡片内继续嵌套卡片；
- 常规圆角不超过 8px，除圆形图标按钮和状态胶囊外；
- 使用统一图标库中的熟悉图标，不手绘纸飞机等老式符号；
- 陌生图标提供 Tooltip；
- 固定工具栏、侧边栏底部账户区和输入控件的尺寸，避免状态变化导致布局跳动；
- 不在界面中持续展示教程、快捷键说明或功能自夸文案；
- 不展示尚未实现或没有真实数据的占位控制。

## 5. 对话空间

### 5.1 左侧边栏

#### 结构

从上到下固定为：

1. `VerityForge` 文字标识；
2. “新建对话”主要按钮；
3. “历史记录”入口及其内联列表；
4. 独立滚动的历史会话区域；
5. 固定在底部的管理员账户区域。

#### 历史记录行为

- 历史记录保留为一个可展开的导航项；
- 点击后直接在侧边栏内部展开列表，不打开抽屉，不跳转到独立页面；
- 再次点击可收起；
- 用户通过侧边栏独立滚动区域向下寻找旧会话；
- 采用连续加载或无限滚动，不显示突兀的“查看更多”按钮；
- 点击会话后恢复该会话的完整消息、当前模式、知识范围和 Metadata 筛选状态；
- 展开历史记录不会推动底部账户区域，`Administrator` 始终固定在原位；
- 顶部品牌与“新建对话”也不随历史列表滚动。

#### 历史会话条目

默认只展示：

- 根据首轮内容自动生成的会话标题；
- 最近活动时间。

不在列表中堆叠知识库、模式、消息数量等次要信息。鼠标悬停时可提供：

- 重命名；
- 置顶；
- 删除。

当前会话以克制的背景或左侧指示线表示，不使用强烈高亮卡片。

#### 账户区

- 当前只显示管理员账户；
- 固定在侧边栏底部；
- 账户菜单中提供进入管理工作台、账户相关操作和退出；
- 不因历史记录数量、展开状态或主内容滚动而移动。

### 5.2 空白对话页

空白页只保留：

- 一句简短问候；
- 对话输入区。

删除以下内容：

- 机器人或项目装饰图标；
- “可信知识问答”等眉题；
- 冗长的大标题和说明段落；
- 任务示例卡片；
- 功能介绍卡片；
- 重复品牌名；
- 固定快捷键教学。

输入区应是首屏最明确的交互焦点，而不是被说明文字和辅助组件包围。

### 5.3 对话输入区

#### 输入能力

当前仅支持文本对话，不提供：

- 文件上传；
- 图片上传；
- 代码附件；
- 附件按钮；
- 多用途加号按钮。

文本编辑器为一个可随内容自然增高的整体输入区。

#### 控件层级

输入区下方或内部工具栏只保留三类控制：

1. 知识范围：可选；
2. Metadata 筛选：可选；
3. 运行模式：必选，但有系统默认值。

右侧为圆形上箭头发送按钮。生成过程中，同一位置切换为停止按钮，避免增加第二个并列动作。

#### 运行模式

模式固定为：

- `自动`：默认值，可使用 Sparkles 等表示智能选择的图标；
- `快速`：可使用 Zap 等表示速度的图标；
- `深度`：可使用 Telescope 等表示深入检索的图标。

三种模式是必选项，但用户无需每次手动选择，因为默认使用“自动”。模式不以三个同等重量的大胶囊长期占据输入区，而是通过紧凑的分段控件或菜单切换。

模式一经选择，持续作用于整个当前对话，直到用户手动切换。切换只影响后续消息，不回溯重算已有答案。

#### 知识范围

- 知识库选择是可选项；
- 未选择时默认在当前管理员可访问的全部知识范围中检索；
- 支持同时选择多个知识库；
- 选择结果持续作用于当前对话，直到清除或切换；
- 修改只影响后续消息。

#### 筛选状态摘要

输入区不长期铺开所有条件。折叠状态只显示简短摘要，例如：

- `2 个知识库 · 3 个筛选条件`；
- `全部知识 · 3 个筛选条件`。

点击摘要后再进入完整的知识范围和 Metadata 筛选界面。

### 5.4 对话消息与答案

#### 消息布局

- 用户消息使用轻量、靠右的消息气泡；
- 助手回答采用靠左的无框文章布局；
- 不为每条消息重复显示头像、“你”或“RAG”等标签；
- 正文宽度适合阅读，不横跨整个超宽屏幕；
- 代码、表格和引用按内容类型单独优化，不将整个回答放入厚重卡片。

#### 引用与来源

- 正文中使用紧凑的行内引用标记；
- 回答末尾显示 `来源 · N`；
- 点击后展开来源详情，而不是永久占据右侧空间压缩正文；
- 来源详情包含文档标题、所属知识库、章节或页码、命中的原文片段、更新时间和“打开原文”；
- 点击来源能够定位到知识库中的相应文档和正文位置；
- 默认不展示向量距离、重排分数、召回分数等开发指标；
- 研发调试信息仅在需要时进一步展开。

### 5.5 对话 Metadata 筛选

#### 作用范围

- Metadata 筛选作用于一个或多个已选知识库；
- 未选择知识库时，筛选作用于管理员当前可访问的全部知识库；
- 先进行可访问范围校验，再进行文档级 Metadata 过滤；
- 只在通过过滤的当前有效文档版本中检索 Chunk。

#### 条件组合

- 不同字段之间使用 `AND`；
- 同一字段选择多个值时使用 `IN`，在用户语义上表现为“任一值”；
- 界面使用自然语言，不暴露 `GTE`、`LTE` 等技术操作符。

#### 时间字段

时间字段至少支持：

- 等于某日；
- 早于；
- 早于或等于；
- 晚于；
- 晚于或等于；
- 位于某个时间范围。

例如，“上传时间为 2026 年 3 月以后”按 Asia/Shanghai 时区解释为：

```text
upload_time >= 2026-03-01 00:00:00
```

这里的 `upload_time` 是上传前已经准备并随文档导入的文档级 Metadata，不是从文档内容中解析出来的业务时间、发布日期或事件时间。本版本不从正文推断日期。

#### 会话持久性

Metadata 筛选条件持续作用于整个当前对话，直到用户手动修改或清除。修改只影响后续消息。

## 6. 评测工作台

### 6.1 核心用户任务

评测模块只围绕以下任务组织：

1. 创建评测；
2. 查看评测进度；
3. 查看评测结果指标；
4. 查看每一个样例的具体情况；
5. 明确显示本次评测采用的模式。

不再把数据集、配置、回归计划、趋势、样例详情和运行历史同时塞在一个长页面中。

### 6.2 页面结构

#### A. 评测列表页

用于查找和管理评测运行，列表展示：

- 评测名称；
- 模式；
- Query 文件或数据集名称；
- 状态与进度；
- 一个最关键的结果摘要；
- 创建时间。

页面唯一主要操作为“新建评测”。

#### B. 新建评测流程

创建一次评测至少需要：

- 上传 Query 文档；
- 选择本次评测模式；
- 选择一个或多个知识库。

评测名称默认由“文件名 + 模式 + 时间”生成，并允许管理员修改。

Query 文件首选 `.xlsx`，产品提供模板下载。CSV 可作为后续兼容格式；首版不向管理员暴露 JSONL。

Query 模板预计包含问题文本、标准答案、预期引用文档和分类标签等评测所需信息，但最终字段不能凭设计假设确定。实施计划制定前必须核验仓库或历史 Codex v8 评测实验的真实输入、配置和结果格式，并据此确定模板。

#### C. 评测运行详情

运行中页面只突出：

- 当前状态；
- 总体进度；
- 已完成数量；
- 执行失败数量；
- 当前处理阶段；
- 本次使用的模式和知识库。

运行尚未完成时，不展示空白的结果图表、趋势模块和无数据卡片。

运行完成后，详情页按以下层级展示：

1. 关键指标；
2. 问题或失败分布；
3. 样例列表；
4. 完整运行信息。

#### D. 样例详情

每个样例详情展示：

- Query；
- 实际答案；
- 标准答案或期望信息；
- 引用来源；
- 链路执行状态；
- 质量指标及原因；
- 必要时展开的检索和处理阶段信息。

样例详情使用完整页面或足够宽的详情区域，不能塞入狭窄弹窗。

#### E. 对比视图

一次评测只运行一个模式，不在创建时同时启动 Fast 和 Deep。

管理员可在评测完成后，另行选择多次运行进入独立对比视图。Fast/Deep 对比不是每个评测详情页永久存在的控制。

### 6.3 模式规则

每次评测必须选择且只选择一个模式：

- `自动`；
- `快速`；
- `深度`。

运行详情和列表都应明确展示实际使用的模式，确保结果可解释、可复现。

### 6.4 链路成功与质量指标

评测必须严格区分两类结果：

#### 执行或链路状态

只要请求完整经过 RAG 链路并正确获得最终答案，即视为本次样例“执行成功”。该状态用于衡量模型 API 超时、服务异常或链路中断等运行可靠性。

因此界面使用以下术语：

- `执行成功率`；或
- `链路成功率`。

不使用含义模糊的“通过率”。

#### 答案质量

答案是否准确、完整、忠实、引用正确，由独立质量指标衡量。执行成功不代表答案质量合格，质量较低也不代表链路执行失败。

每个样例先展示执行状态，再展示质量指标，避免将两者混为一个红绿结论。

### 6.5 超时与重试

遇到模型 API 超时或可重试的临时错误时：

1. 系统自动重试两次；
2. 运行界面显示“重试中”及当前次数；
3. 重试耗尽后将该样例标记为执行失败；
4. 失败不阻塞其他样例继续运行；
5. 运行结束后支持仅重跑失败样例。

### 6.6 可复现性

每次评测记录：

- 运行模式；
- Query 文件版本或哈希；
- 所选知识库；
- 知识库版本或内容快照；
- 模型与检索链路版本；
- 开始和结束时间；
- 相关运行配置快照。

如果后端尚无正式知识库版本号，至少记录知识库 ID、最后更新时间和内容修订哈希。页面顶部只需展示模式和知识库，完整技术信息收纳在“运行信息”中。

## 7. 知识库工作台

### 7.1 设计参考与取舍

知识库模块参考 WeKnora 的对象模型和可观察性，包括知识库、文档、分块、处理过程和原文定位等能力。

参考不等于照搬。VerityForge 不采用层层嵌套的抽屉、弹窗或卡片堆叠，而是根据本项目的管理员任务重新组织为列表页、完整详情页和标签页。

参考位置：

- 本地参考仓库：私有 WeKnora 工作副本；
- 参考页面：隔离环境中的 WeKnora Knowledge Base 页面。

### 7.2 知识库列表页

使用紧凑表格或行式列表，不使用大面积重复卡片。每行展示：

- 知识库名称和简短描述；
- 就绪文档数 / 总文档数；
- 处理中数量；
- 失败数量；
- Chunk 数量；
- 最近更新时间。

页面唯一主要操作为“新建知识库”。

创建知识库时只要求：

- 名称；
- 描述。

Metadata 公共结构和处理配置由系统默认挂载，不要求管理员在创建时进行复杂配置。

### 7.3 知识库详情页

知识库详情使用完整页面，顶部只展示：

- 知识库名称；
- 简短健康状态；
- “上传文档”主要操作。

主体使用标签页：

- `文档`：默认标签；
- `Metadata`：查看公共字段结构和导入规则；
- `索引/设置`：查看必要的索引状态和知识库级信息。

文档列表上方保留搜索和一个统一“筛选”入口。已生效的筛选条件以可删除的紧凑标签显示。

不再把 Metadata Schema 编辑器和索引配置面板永久放在文档列表上方。

### 7.4 文档列表

文档列表至少支持：

- 按文件名搜索；
- 按处理状态筛选；
- 按文档级 Metadata 筛选；
- 查看当前版本；
- 查看处理状态与更新时间；
- 进入文档完整详情；
- 上传新版本；
- 重新处理；
- 软删除。

Metadata 筛选规则与对话空间保持一致，不为管理页面另外发明一套操作语义。

### 7.5 文档详情页

文档详情必须使用独立完整页面，不采用狭窄弹窗或抽屉。页面分为：

- `内容`；
- `分块`；
- `Metadata`；
- `处理过程`；
- `版本`。

当前只有 `ADMIN`，因此不展示权限标签页或成员授权控件。

#### 内容

默认展示解析和规范化后的文本，因为这是检索链路实际使用的内容。

提供紧凑切换：

- `解析文本`；
- `原文件`。

原文件预览或下载是次要能力。用户从引用或 Chunk 点击“定位原文”时，应切换到正确内容视图并定位到对应位置。

#### 分块

分块页面只读，行为参考 WeKnora。每个 Chunk 可展示：

- 父子关系；
- 顺序；
- Token 数量；
- 文本内容；
- 启用状态；
- 定位原文；
- 复制内容。

本版本不提供：

- Chunk 手动新增、删除或编辑；
- Chunk Metadata 展示；
- 向量内容或向量坐标；
- 原始 Source Map 和偏移量等开发数据。

如果分块效果不理想，管理员通过全局运行配置调整规则后重新处理文档，而不是直接修改单个 Chunk。

#### Metadata

展示文档上传前已经准备并导入的文档级 Metadata。所有可见字段允许管理员后续手动修改，并记录修改历史。

纯筛选类 Metadata 修改后应立即影响后续检索，不需要重新进行向量化。系统内部仍保留不可变审计事实，以确保数据真实性和问题追踪能力。

#### 处理过程

处理过程以阶段时间线或阶段列表展示：

1. `PARSE`：解析；
2. `NORMALIZE`：规范化；
3. `CHUNK`：分块；
4. `EMBED`：向量化；
5. `PUBLISH`：发布可检索版本。

页面展示：

- 总耗时；
- 每个阶段的状态；
- 开始时间、结束时间和真实耗时；
- 关键产出数量；
- 错误原因；
- 自动重试次数。

点击阶段后再展开详细日志和错误，不在主页面铺满技术信息。首版只要求阶段级可观察性，不要求完整展示类似追踪系统的嵌套 Span 树。

失败后的人工操作为“重新处理整个文档”，暂不支持从任意阶段断点续跑。

#### 版本

- 文档版本通过明确的“上传新版本”动作创建；
- 不仅依赖同名文件自动判断；
- 使用稳定的 `document_key` 关联同一业务文档；
- 每个版本具有业务版本号；
- 新版本完成处理后再原子切换为当前版本；
- 历史版本继续保留并可追溯；
- 正常对话和评测检索只使用当前生效版本。

## 8. 文档级 Metadata 规范

### 8.1 层级定义

系统区分两层 Metadata：

#### 文档级 Metadata

- 在上传前已经由业务侧准备好；
- 随文件一起导入；
- 不从文件正文中解析或推断；
- 用于管理、版本、生命周期和检索前过滤；
- 允许管理员后续修改。

#### Chunk 级 Metadata

- 在解析、分块和入库过程中由系统生成；
- 用于引用溯源和内部链路；
- 当前知识库界面不展示；
- 后端仍应保留 Chunk 到文档、版本、章节和原文位置的映射。

### 8.2 公共字段

首版采用统一的组织级公共 Metadata 字段，不允许每个知识库自行定义同名不同义的字段。这样才能在多个知识库上稳定筛选。

用户可见字段：

| 字段 | 含义 | 是否必填 | 是否可修改 | 筛选方式 |
| --- | --- | --- | --- | --- |
| `document_key` | 同一业务文档跨版本的稳定标识 | 是 | 是，需校验关联影响 | 精确 |
| `file_name` | 本次上传文件名和匹配键 | 是 | 是 | 模糊、精确 |
| `upload_time` | 业务侧在上传前提供的上传时间 | 是 | 是 | 精确、早于、晚于、范围 |
| `file_type` | 声明的文档类型，如 PDF、HTML、DOCX | 是 | 是 | 单选、多选 |
| `version` | 业务版本号 | 是 | 是 | 精确 |
| `organization` | 所属组织 | 是 | 是 | 单选、多选 |
| `department` | 所属部门 | 是 | 是 | 单选、多选 |
| `category` | 医疗、商业等所属种类 | 是 | 是，可多值 | 单选、多选 |
| `valid_to` | 失效时间 | 否 | 是 | 精确、早于、晚于、范围、是否为空 |

`upload_time` 明确不代表从文档中提取的业务日期。首版不增加 `document_date` 字段。

### 8.3 系统审计字段

为了保证真实性，系统内部保留不可变或受保护的审计数据，例如：

- 实际进入系统的时间；
- 实际检测到的 MIME 类型；
- 文件哈希；
- 内部文档 ID 和版本 ID；
- 操作管理员；
- Metadata 修订记录；
- 处理配置版本。

这些数据不需要全部出现在普通详情页，但用于审计、冲突检测和问题定位。用户修改可见 Metadata 时不会覆盖这些系统事实。

### 8.4 批量导入方式

首版面向管理员采用：

```text
文档文件 + metadata.xlsx
```

内部服务使用规范化 JSON 表示；JSONL 可作为后续 API 或批处理格式，但首版不暴露在管理界面。

`metadata.xlsx` 至少包含以下列：

```text
document_key
file_name
upload_time
file_type
version
organization
department
category
valid_to
```

约定：

- `category` 多值使用英文分号分隔；
- 日期按模板明确的格式和 Asia/Shanghai 时区解析；
- `file_name` 用于将 Metadata 行与上传文件匹配；
- `document_key + version` 必须唯一；
- 上传前先完成校验，再允许进入处理链路。

### 8.5 导入校验

上传确认页分级展示：

- 已匹配且可上传；
- 文件存在但缺少 Metadata；
- Metadata 存在但找不到文件；
- `document_key + version` 重复；
- 必填字段缺失；
- 字段类型或日期格式错误；
- 组织、部门或种类不在公共字典中；
- 声明文件类型与实际 MIME 不一致。

声明类型与检测 MIME 不一致时提示警告，实际解析器以检测到的 MIME 为准。管理员修正错误后再继续，不让问题文件静默进入知识库。

### 8.6 多知识库一致性

- `organization`、`department`、`category` 等公共字段在所有知识库使用稳定字段 ID 和类型；
- 部门值来自统一组织部门字典；
- 种类值来自统一分类字典；
- 多知识库筛选只展示在所选范围内语义一致的字段；
- 首版只开放公共字段，暂不开放每个知识库自定义扩展字段；
- Metadata 过滤先匹配文档，再在匹配文档的当前版本 Chunk 中检索。

### 8.7 失效规则

达到 `valid_to` 的文档默认自动退出对话和评测检索，但仍保留在管理工作台中，不被物理删除。管理员修改或清空失效时间后，可以重新使其参与检索。

管理页面应明确显示“已失效”状态和失效原因，避免管理员误以为文档处理失败或被删除。

## 9. 处理配置

首版统一使用一套系统默认处理配置，包括：

- 解析器选择规则；
- 规范化规则；
- 分块规则；
- Embedding 模型；
- 发布和索引规则。

约束如下：

- 不提供每个知识库独立的解析、分块或模型配置；
- 新建知识库自动继承当前系统默认配置；
- 新上传和重新处理使用当时的系统默认配置；
- 每次文档处理都记录实际使用的配置版本快照；
- 历史版本继续保留其原配置记录；
- 只有管理工作台的“运行配置”模块可以修改系统默认配置。

## 10. 渐进式信息展示

所有复杂模块统一采用分级展示：

### 第一级：列表

只回答“这是什么、现在怎样、下一步点哪里”。

### 第二级：对象详情

展示一个对话、评测或文档的主要内容和关键状态。

### 第三级：维度标签

按内容、分块、Metadata、处理过程、版本等维度切换，不在同一长页同时展开。

### 第四级：技术细节

检索分数、运行日志、阶段错误、版本哈希、配置快照等只在明确点击后出现。

这一原则用于解决当前“内容很多，但重点看不到”的问题。减少信息并不等于删除可追溯性，而是让信息在正确的时机出现。

## 11. 状态与反馈规则

- 加载、空状态、失败和部分成功必须有明确且可行动的反馈；
- 空页面不展示不存在的数据模块；
- 处理失败应说明失败阶段、原因和可执行的下一步；
- 批量任务允许部分成功，不因单个对象失败中断全部任务；
- 重试状态和次数可见；
- 删除采用软删除并提供必要确认；
- 破坏性操作使用红色，但不让整个页面充斥风险色；
- 成功状态不使用大面积绿色庆祝组件；
- 页面主要操作在固定、可预测位置，避免滚动后难以寻找。

## 14. 验收基线

后续视觉稿和实现至少满足以下要求：

### 全局

- 仅针对桌面端设计，常见桌面宽度下无重叠、截断和异常留白；
- 同一页面有清晰的单一主要任务；
- 页面不依赖大量卡片、描边和阴影维持层级；
- 关键控件位置稳定，展开内容不推动固定导航和账户区；
- 所有可见操作都有真实行为，不放装饰性伪控件。

### 对话

- 侧边栏只包含品牌、新建对话、内联历史记录和账户；
- 历史记录独立滚动，账户固定底部；
- 空白页只保留简短问候和输入区；
- `自动 / 快速 / 深度` 为必选模式且默认自动；
- 知识范围与 Metadata 为可选并在当前会话持续生效；
- 发送按钮为现代圆形上箭头，生成时变为停止；
- 助手答案可连续阅读，来源按需展开并可定位原文。

### 评测

- 创建、进度、结果、样例和运行信息有明确层级；
- 每次运行只有一个模式；
- 执行成功与答案质量分开呈现；
- API 超时自动重试两次，耗尽后不阻塞其余样例；
- 运行中不展示空结果模块；
- 每个样例可以独立查看实际答案、来源、状态和指标。

### 知识库

- 知识库与文档采用列表和完整详情页；
- 文档详情包含内容、分块、Metadata、处理过程和版本；
- Chunk 只读且可定位原文；
- 处理过程展示真实阶段耗时和错误；
- 文档级 Metadata 在上传前导入，可后续修改；
- 多知识库使用统一公共字段筛选；
- 正常检索只使用当前有效版本和未失效文档；
- 处理配置统一使用系统默认并记录版本快照。
