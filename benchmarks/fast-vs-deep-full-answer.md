# Fast / Deep 五题完整回答验收

评测日期：2026-08-07

## 目的与口径

200 题主报告跳过最终回答，适合定位检索和证据问题；本报告选择 5 个困难多目标案例，完整执行检索、证据装包、最终生成、引用持久化与模型 Judge，并用相同问题对照 Fast 与 Deep。

- 案例：ARH-001、ARH-021、ARH-036、ARH-046、ARH-051。
- Deep Read：按 Goal 批量读取父块。
- 最终装包：`UNIQUE_PARENT_GOAL_COVERAGE_TOKEN_BUDGET`。
- 最终输入 / 输出预算：20,000 / 4,000 Token。
- 执行环境：隔离数据库副本和隔离 API 容器。
- Judge：最终答案语义与引用支持均开启模型评判。

评测 Artifact 当时使用历史内部 Pipeline 名；公开源码已把同一最终链路统一为 `deep-rag-final`。本报告只使用运行事实，不要求当前代码依赖那个历史名称。

五题共同满足：

1. Accepted 唯一父块数等于 Packed 唯一父块数，没有固定条数的提前截断。
2. Packed 父块 ID 无重复，跨 Goal 的相同父块只序列化一次。
3. 所有实际引用指向父块证据，引用正文与保存的父块一致。
4. 引用位置覆盖父块全部 Source Anchor Segment 的最小起点到最大终点。
5. 最终回答只调用一次模型。

在这组刻意选择的困难多目标题上，Deep 的检索、答案覆盖、语义正确性和引用支持均领先，但平均耗时约为 Fast 的 3.7 倍。额外时间主要来自 Goal 研究、父块 Deep Read、Evidence Judge 和更大的最终上下文，并非多次最终答案生成。

AEC 不能用于直接惩罚 Fast：Fast 的证据契约是检索 Trace 与上下文 Chunk，不执行 Deep 的 Accepted Evidence 阶段。跨模式比较应优先使用 Recall、最终回答覆盖、语义、引用支持和时延。

## 在线问题复验

另用 Kubernetes 普通用户、ServiceAccount、匿名请求与 RBAC 的多 Goal 问题复验：

- 首次运行在最终生成阶段收到模型空流，检索与装包已经成功。
- 第二次运行成功：Accepted 12、唯一父块 12、Packed 12、实际引用 10。
- 最终请求输入 / 输出为 16,019 / 1,301 Token，最终生成 24.8 秒，全链路约 90 秒。
- 回答按普通用户、ServiceAccount、匿名请求分层，并分别覆盖身份来源、凭据管理和 RBAC。

该复验确认“Accepted 多、最终父块少”的旧装包问题已由唯一父块 + Goal 覆盖 + Token 预算策略消除。

## 稳定性记录

首次以案例并发 4 运行时只有 2/5 严格成功；失败均来自模型空流或模型逻辑调用失败。将案例并发降为 1 并增量续跑后，其余 3 题恢复，最终 5/5。Deep 内部搜索、Rerank 和 Deep Read 并发仍保持 6 / 3 / 3。

因此验收结论分为两部分：

- 证据装包、回答结构和引用正确性：通过。
- 上游模型单次成功率：存在波动，需要可恢复运行和增量续跑；不能通过减少证据来掩盖稳定性问题。

## 样本限制

5 题不足以估计所有问题分布的最终答案质量。它是对 200 题检索评测的补充，证明完整链路和引用契约可工作；整体回归仍应同时查看 [200 题报告](deep-rag-final-200-case.md)。
