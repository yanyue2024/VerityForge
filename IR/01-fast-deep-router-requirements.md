# Fast / Deep 问题路由器需求文档

> 文档状态：开发基线
> 基线版本：Agentic RAG v8
> 编写日期：2026-07-28
> 适用模式：`AUTO` 选择 `FAST` 或 `DEEP`

## 1. 背景

当前系统已经具备两条可独立工作的回答链路：

- `FAST`：单问题双路召回、RRF、本地 Rerank、上下文扩展和一次回答生成；
- `DEEP`：最多三个 Goal、Goal 内双路检索、父块与 Span 深读、一次 Evidence Judge、最多一次补检和最终回答。

v8 的 Deep 检索质量已经达到较高水平。最终 200 题严格健康结果的 Recall@5 为 `0.963333`，但研究阶段平均消耗约 `16,345` Token、`46.850` 秒。对于文档和章节已经明确的单跳问题，完整 Deep 链路会消耗不必要的规划、Deep Read 和 Judge 成本。

当前 `AUTO` 并没有实际路由：`RunCoordinator.selectMode` 对所有 `AUTO` 请求固定返回 `DEEP`。仓库虽然保留旧 LLM Router 接口和 `ROUTING_ONLY` 评测能力，但旧方案会增加模型 Token、网络延迟和后端失败面，不满足本次“低成本、快速”的核心目标。

## 2. 目标

构建一个由服务端执行的低成本问题路由器，在用户选择 `AUTO` 时快速判断：

```text
适合单文档、单目标直接检索的问题 -> FAST
需要拆解、比较、综合或存在检索风险的问题 -> DEEP
判断不确定                         -> DEEP
```

路由器必须实现以下结果：

1. 路由过程不调用生成式大模型，新增 Token 为 `0`；
2. 路由判断在本地完成，不引入外部网络请求；
3. 显式 `FAST`、`DEEP` 用户选择保持绝对优先，不被路由器覆盖；
4. `AUTO` 不再固定走 Deep；
5. 以 Recall@5 `>= 0.90` 作为默认质量底线，但优先选择更高的实际收益点；
6. 在既有 Fast / v8 Deep 逐题结果上离线回放，不重新运行两套基线；
7. 输出 Fast 比例、Deep 比例、Recall@5/10、Token、延迟和相对全 Deep 的变化；
8. 路由理由、决策来源和选择模式必须进入现有事件及评测诊断。

## 3. 非目标

本次不做以下工作：

- 不修改 Fast RAG 的检索、Rerank 或回答逻辑；
- 不修改 v8 Deep 的 Planner、Deep Read、Judge 或最终排序；
- 不重新运行 Fast 或 Deep 的完整实验；
- 不使用开放式 ReAct Router；
- 不训练新模型，不调用远程分类模型；
- 不根据知识库内容执行一次预检索后再决定模式；
- 不把离线基准题的 `challengeType`、答案或期望文档作为线上特征。

## 4. 用户场景

### 4.1 明确单文档、单章节直查

```text
根据《Pod 的生命周期》，该章节给出的关键信息是什么？
```

预期：`FAST`。问题目标唯一、文档锚点明确，不需要 Goal 拆解。

### 4.2 多目标或跨文档综合

```text
综合《Pod 的生命周期》与《Job》，分别说明两者的关键约束。
```

预期：`DEEP`。存在两个独立目标和答案组织约束。

### 4.3 三阶段或多步骤研究

```text
制定三阶段核查方案，依次处理部署、配置和故障恢复。
```

预期：`DEEP`。需要稳定 Goal、证据面和独立证据池。

### 4.4 单目标且有稳定技术标识

```text
团队不记得资料名，需要确认 ResourceClaimSpec 的作用。
```

预期：在没有比较、综合、多目标等风险信号时可走 `FAST`。稳定技术标识能够让双路检索形成高精度锚点。

### 4.5 信息不足或判断不确定

```text
这个系统问题怎么处理？
```

预期：`DEEP`。默认 Deep 是质量保护策略，不允许为了提高 Fast 比例强行分类。

## 5. 功能要求

### FR-1：三段式确定性决策

路由器按固定优先级执行：

1. 强 Deep 信号命中时立即选择 `DEEP`；
2. 没有强 Deep 信号且命中高置信 Fast 信号时选择 `FAST`；
3. 其余情况选择 `DEEP`。

### FR-2：强 Deep 信号

至少覆盖：

- 两个及以上显式文档或目标；
- “同时、分别、依次、第一阶段/第二阶段、三阶段、独立目标”；
- “综合、比较、对比、差异、权衡、冲突、跨文档、多份资料”；
- 需要原因与方案、诊断与修复等组合任务；
- 明显要求按多部分组织答案。

### FR-3：高置信 Fast 信号

至少覆盖：

- 单一《文档》或单一章节明确直查；
- 简单的“是否给出/是否包含/是否规定”型资料存在性问题；
- 单一目标中存在长度不少于 3 的稳定 ASCII 技术标识，例如 `Kubernetes`、`ResourceClaim`、`Webhook`、`CSS-in-JS`，且没有强 Deep 信号。

技术标识规则不得把普通英文疑问词当作锚点，也不得覆盖强 Deep 判断。

### FR-4：安全默认值

空问题、规则异常、未识别表达和低置信问题一律选择 `DEEP`。路由器不能因内部异常中止整个 RAG Run。

### FR-5：可观测性

`ROUTE_SELECTED` 至少包含：

- requested mode；
- selected mode；
- 稳定的 reason code；
- 决策来源为 `HEURISTIC`；
- 可用于诊断的简短信号说明。

不得在 reason 中写入原问题全文或敏感内容。

### FR-6：评测兼容

现有 `ROUTING_ONLY` 评测必须能够直接调用新路由器；`routeDecisionSource` 应继续统计为 `HEURISTIC`，模型尝试数和 Fallback 数应为零。

## 6. 非功能要求

| 维度 | 要求 |
|---|---|
| Router Token | 每题 `0` |
| 外部调用 | 每题 `0` |
| 时间复杂度 | 相对问题长度 `O(n)` |
| 单题本地延迟 | P95 `< 2 ms`（不含评测框架和数据库） |
| 可重复性 | 同一标准化问题必须得到相同决策和 reason code |
| 线程安全 | 无可变共享状态，可被并发调用 |
| 失败策略 | Fail Deep |
| 兼容性 | 显式 Fast/Deep 行为不变；Deep v8 链路不变 |

## 7. 质量与收益基线

既有 200 题 Agentic Retrieval 困难集可按 `benchmarkCaseId` 配对：

| 基线 | Run / 结果 | Recall@5 | 平均研究 Token | 平均研究延迟 |
|---|---|---:|---:|---:|
| Fast 检索代理 | `9da94cf0-...` | 0.606667 | 0 | 约 0.82 秒 |
| v8 Deep 四批健康结果 | 四个 50 题 Run | 0.963333 | 16,345 | 46.850 秒 |

这里的 Fast 是与 Fast 主检索同构的“原问题 Keyword + Semantic + RRF”历史 Retrieval-only 结果；Deep 也是跳过最终回答的研究阶段结果。因此 Token 和时间验收只描述检索/研究阶段，不宣称是完整最终回答端到端成本。

## 8. 验收标准

### 8.1 硬门槛

- `AUTO` 确实产生 Fast 和 Deep 两种选择；
- Router 本身新增 Token、模型调用和网络调用均为 0；
- 困难 200 题离线回放 Recall@5 `>= 0.90`；
- 相对全 Deep，研究 Token 至少节省 `5%`；
- 相对全 Deep，平均研究阶段时间至少节省 `5%`；
- 显式 Fast/Deep 单元测试保持通过；
- 路由异常或不确定表达全部 Fail Deep。

### 8.2 目标值

初步收益计算表明，以下策略优于更激进的分流：

```text
复杂信号 -> Deep
单文档明确直查 -> Fast
稳定技术标识且无复杂信号 -> Fast
其余 -> Deep
```

在困难 200 题既有结果上的预期是：

- Fast 28 题，Deep 172 题；
- Recall@5 保持 `0.963333`，下降 `0`；
- 研究 Token 节省约 `9.37%`；
- 平均研究延迟节省约 `9.26%`。

最终以生产代码实际决策回放结果为准，不以文档中的预估替代验收。
