# Fast / Deep Router 质量成本曲线实验

> 文档状态：候选方案对比，不代表生产默认值
>
> 基线版本：Agentic RAG v8，提交 `8af4175`
>
> 实验日期：2026-07-28
>
> 实验方式：复用既有 Fast / Deep Artifact 离线回放，新模型调用为 0

## 1. 实验目的

上一版 Router 停在 Recall@5 无损的保守点：研究 Token 节省 `9.37%`。本轮放宽目标，不再要求 Recall 无损，而是给出从约 `20%` 到 `60%` Token 节省的多组可选方案，由系统负责人结合质量、成本、复杂度和风险自行选择。

本轮不修改当前生产 Router 默认规则，不重新运行 Fast 或 Deep，不使用期望答案、期望文档、Case ID 或题型标签作为线上路由特征。

## 2. 数据与口径

Fast 使用历史 Run：

```text
9da94cf0-7e48-4f44-b216-ccd032411bfe
```

v8 Deep 使用四批严格健康 Run：

```text
196f3c20-c164-4dfb-8e1f-8f852e5f8ba8
c499ed92-c3f7-4bdf-aec1-7a5b9184523f
ffae8878-105a-44cf-9159-ac313794ed0d
1d3cc762-df84-4821-b34f-93d3634341b9
```

200 题按 `benchmarkCaseId` 配对，双方均为成功结果。Deep 基线为：

| 指标 | v8 全 Deep |
|---|---:|
| Recall@5 / Recall@10 | 0.963333 / 0.963333 |
| MRR@5 | 0.947500 |
| RCC | 0.821195 |
| AEC | 0.501906 |
| 研究 Token | 3,269,084 |
| 平均 / P50 / P95 | 46.850s / 45.156s / 74.449s |

Fast Artifact 是原问题 Keyword Top30 与 Semantic Top30 并发召回、RRF Top40 的 Retrieval-only 结果，生成式研究 Token 记为 0。Deep Artifact 包含 Planner、Deep Read 和 Judge 的研究 Token。双方均跳过最终回答生成，因此本报告中的 Token 和时间是研究阶段口径，不是完整端到端回答成本。

## 3. 两类可部署方案

### 3.1 纯文本 Router

只读取用户问题，延迟可忽略，不执行预检索。可用信号包括：

- 当前 Deep veto：多目标、分阶段、比较、冲突、综合等；
- 稳定 ASCII 技术锚点数量；
- 单目标或多目标结构。

优点是架构简单。缺点是无法知道 Fast 是否已经找到了问题中的目标文档，放宽到 50% 成本点时误放较多。

### 3.2 检索感知 Router

先执行一次低成本 Fast 预检索：

```text
原问题
-> Keyword Top30 + Semantic Top30
-> RRF Top40
-> 读取 Top5 文档标题和分数
-> 本地置信度判断
-> FAST：复用预检索结果继续 Fast
-> DEEP：升级到 v8 Deep
```

预检索不调用生成式模型。本报告的时间已经按以下方式计算：

```text
选择 Fast：Fast 预检索时间
选择 Deep：Fast 预检索时间 + Deep 研究时间
```

因此没有把预检索开销隐藏在节省率之外。

核心运行时特征 `titleHitCount` 定义为：

1. 读取 Fast RRF Top5 文档标题；
2. 标题至少 4 个字符；
3. 大小写归一化后，完整标题出现在原问题中；
4. 统计命中的不同 Top5 标题数量。

它只使用问题和实时检索结果，不读取评测标签。多目标、分阶段和单目标由现有 Router 结构信号识别。评测 SQL 中的题型字段仅用于聚合；200 题上，多目标/分阶段结构信号与对应结构分组为 100% 映射。

## 5. 每个档位的规则

### 5.1 纯文本 22

```text
没有任何强 Deep 结构信号 -> Fast
存在多目标、分阶段、比较、综合、冲突等 -> Deep
```

它相当于让全部单目标困难题走 Fast。实现成本最低，Token 达到 `22.04%`，但 Recall@5 直接降到 `0.883333`。

### 5.2 检索感知 28

```text
当前 Quality 高置信 Fast
OR 多目标且 titleHitCount >= 2
OR 分阶段且 titleHitCount >= 2
-> Fast
其余 -> Deep
```

结果：Token 节省 `27.58%`，Recall@5 `0.936667`，RCC 还高于全 Deep `0.008649`。这是质量优先的扩展档位。

### 5.3 检索感知 39

```text
当前 Quality 高置信 Fast
OR 多目标且 titleHitCount >= 1
OR 分阶段且 titleHitCount >= 3
-> Fast
其余 -> Deep
```

结果：Token 节省 `38.89%`，Recall@5 `0.893333`，Recall@10 `0.900833`。这是接近 0.90 Recall 的成本优先平衡点。

### 5.4 检索感知 50

```text
当前 Quality 高置信 Fast
OR 多目标且 titleHitCount >= 1
OR 分阶段且 titleHitCount >= 2
-> Fast
其余 -> Deep
```

结果：Token 节省 `50.16%`，时间节省 `50.04%`，Recall@5 `0.866667`，MRR@5 `0.927667`，RCC `0.802234`。

相同 Token 节省下，纯文本方案 Recall@5 只有 `0.808333`。检索感知使 Recall 提高 `0.058334`，MRR@5 提高 `0.087250`，RCC 提高 `0.026631`。

### 5.5 检索感知 61

```text
当前 Quality 高置信 Fast
OR 所有双目标问题
OR 分阶段且 titleHitCount >= 2
-> Fast
其余 -> Deep
```

结果：Token 节省 `60.91%`，Recall@5 `0.806667`。该档位适合作为极限成本实验，不适合作为当前默认值。

## 7. 理论上界

为判断是否还有优化空间，额外计算了一个不可上线的逐题理想选择器：按历史 Fast 相对 Deep 的实际 Recall 损失和可节省 Token 排序。它使用了结果标签，只能作为上界，不能成为 Router 规则。

| 目标 Token 节省 | 实际节省 | 理想 Recall@5 | Recall@10 | MRR@5 | RCC |
|---:|---:|---:|---:|---:|---:|
| 20% | 20.20% | 0.973333 | 0.973333 | 0.952500 | 0.830304 |
| 30% | 30.03% | 0.973333 | 0.973333 | 0.952500 | 0.828970 |
| 40% | 40.55% | 0.958333 | 0.960000 | 0.946667 | 0.827192 |
| 50% | 50.10% | 0.931667 | 0.940000 | 0.942917 | 0.817552 |
| 60% | 60.36% | 0.890000 | 0.900000 | 0.931583 | 0.798162 |
| 80% | 80.07% | 0.790000 | 0.813333 | 0.904000 | 0.770201 |

50% 点的可部署启发式为 `0.866667`，理论上界为 `0.931667`，仍有约 `0.065` 的探索空间。但要获得这部分收益，需要比标题精确命中更强的置信度估计，并经过独立数据验证。

## 8. 本地轻量模型实验

使用问题结构、技术锚点数、Top5 RRF 分数、标题命中数和问题/标题二元字符相似度作为特征，尝试：

- Ridge；
- Extra Trees；
- Random Forest；
- Gradient Boosting；
- Histogram Gradient Boosting。

验证方式为按 `openeuler / kubernetes / ant-design / apache-doris` 留一项目交叉验证，特征中不包含答案、期望文档、Case ID 或题型标签。

在约 50% Token 节省附近，最好结果为：

| 方法 | Token节省 | Recall@5 | RCC |
|---|---:|---:|---:|
| Random Forest | 51.90% | 0.848333 | 0.780421 |
| Histogram GBDT | 52.29% | 0.851667 | 0.787889 |
| 确定性检索感知 50 | **50.16%** | **0.866667** | **0.802234** |

本地模型没有超过确定性标题覆盖规则，当前 200 题也不足以支撑一个新的模型生命周期。因此本轮不建议为了路由引入训练、发布、阈值漂移和模型监控复杂度。

## 9. AEC 解释

Fast 路径不执行 Deep Read，因此没有 Accepted Evidence。若把 Fast 样本 AEC 记为 0，混合有效 AEC 会随 Fast 比例机械下降：

| 方案 | 有效 AEC |
|---|---:|
| 全 Deep | 0.501906 |
| 当前 Quality | 0.442364 |
| 检索感知 28 | 0.356476 |
| 检索感知 39 | 0.271866 |
| 检索感知 50 | 0.224963 |
| 检索感知 61 | 0.165857 |

这不等价于 Fast 回答没有依据，而是两条链路的证据生产契约不同。混合 Router 应优先比较 Recall、MRR、RCC 和最终答案指标；AEC 应按模式分别展示，不能作为跨模式统一门禁。

## 10. 方案选择建议

### 选择 A：实现最简单

选择纯文本 22：无需 Fast 预检索重构，Token 节省 `22.04%`，Recall@5 `0.883333`。

### 选择 B：质量优先

选择检索感知 28：Token 节省 `27.58%`，Recall@5 `0.936667`，RCC `0.829844`。它在质量和成本上最稳健。

### 选择 C：综合平衡

选择检索感知 39：Token 节省 `38.89%`，Recall@5 `0.893333`，四项目 Recall@5 均不低于 `0.87`。

### 选择 D：明确追求 50% 成本

选择检索感知 50：Token 和时间均节省约 `50%`，Recall@5 `0.866667`，MRR@5 仍为 `0.927667`。这是满足本轮大胆成本目标的首选方案。

### 选择 E：极限成本

选择检索感知 61：Token 节省 `60.91%`，但 Recall@5 降到 `0.806667`，且单项目最低 `0.6867`。只适合显式 Economy 档位或灰度实验。

## 11. 实施边界

在选择检索感知方案后，正式设计必须满足：

1. Fast 预检索结果必须复用，不能进入 Fast 后再次检索；
2. 预检索失败、超时或结果不完整时 Fail Deep；
3. 不读取期望答案、期望文档和评测元数据；
4. 规则档位必须由明确配置选择，不能在代码中同时存在多个模糊阈值；
5. 记录 Profile、titleHitCount、Top5 分数摘要、最终模式和升级原因；
6. 线上按 Profile 分别监控 Recall 代理、追问率、Deep 重试率、Token 和端到端延迟；
7. 新领域先 Shadow，不直接套用当前阈值；
8. 当前 Quality 继续作为回退档位，任何异常均可一键恢复。

## 12. 当前实施状态

系统负责人已选择保留两套检索感知 Profile：

- 默认 `RETRIEVAL_AWARE_50`：多目标至少命中 1 个标题，分阶段至少命中 2 个标题；
- 备选 `RETRIEVAL_AWARE_28`：多目标和分阶段均至少命中 2 个标题。

运行时通过 `RAG_AUTO_ROUTER_PROFILE` 选择，未配置时固定使用 `RETRIEVAL_AWARE_50`。两套 Profile 均执行固定的 `Keyword Top30 + Semantic Top30 -> RRF Top40` 预检索；选择 Fast 时复用预检索结果，预检索失败时回退 Deep。`ROUTE_SELECTED` 记录 Profile、`titleHitCount`、Top5 标题与分数、候选数量和预检索延迟。

切换到质量优先档：

```bash
RAG_AUTO_ROUTER_PROFILE=RETRIEVAL_AWARE_28
```

配置变更需要重启 API。显式 `FAST` 和 `DEEP` 仍然优先于 AUTO Profile，不受该配置影响。
